# テスト設計・整理方針（1.20.1 / Forge）

この文書は `1.20.1-main` のテストを追加・修正・整理するときの初版方針を定める。[PR #1038](https://github.com/hexqua/apprentice_codex/pull/1038) の[テスト設計・整理方針（参照時点）](https://github.com/hexqua/apprentice_codex/blob/f7fa6eab01a1146614d10a8f65ddb79ace098951/docs/testing-policy.md)を基に、Forge、Capability、NBT、依存 MOD の版固有の接続と、[PR #1035](https://github.com/hexqua/apprentice_codex/pull/1035) で修正した確認漏れを考慮する。

この方針を最終形として固定せず、実際の整理で不都合が分かった場合は理由とともに見直す。既存テストの即時適合は要求しない。制定時点ではテスト、製品コード、Gradle、CI の実行対象を変更しない。実行コマンド、必要な検証、失敗時の報告、client 検証の分担は [AGENTS.md](../AGENTS.md) に従う。

## 1. 整理の単位と main との関係

PR #1038 のコミット列を順に cherry-pick して配置・API を直す方法は、この整理の既定手順にしない。共通の検証意図と到達した構成を参考に、現在の 1.20.1 のテストを機能単位で整理する。移動と再分割を繰り返した途中経過を再現する必要はない。

- 共通に守るものは処理結果、状態遷移、拒否境界、保存済み資産の保護とする。
- テスト名、クラス数、パッケージの完全一致、API の一致は目標にしない。共通機能は同じ領域から探せる配置を目指す。
- 1.20.1 固有の挙動・補助処理・回帰テストを、main に存在しないという理由で削除しない。
- main で削除されたテストも、1.20.1 の登録・イベント・保存・通信に固有の故障原因を検出する場合は維持または書き換える。
- main にだけ存在する機能や optional MOD を、構成を合わせるためだけに導入しない。意図した代替仕様はその仕様で検証する。

この方針に基づく 1.20.1 内での再構成は、参考 PR と判断理由を PR 説明等へ記録する。実際に main のコードやコミットを取り込む場合は、既存の backport Skill と `git cherry-pick -x` の規則に従う。この文書は通常の機能 backport の追跡規則を緩和しない。

## 2. 検証するものと整理の判断

実プレイで起きる不具合を検出できる結果と接続を優先する。

- 発動・取消・終了、命中、ダメージ、マナ・弾薬・耐久値の消費、二重実行の防止。
- 装備・交換・解除後の実際の属性、収納・取出し、保存・復元・旧データ移行と返却。
- レシピ選択、タグ解決、登録定義と実際の利用入口の接続。
- 所有権、権限、射程、設置・破壊許可、禁止設定など、server が守る制約。

各テストについて「どの不具合で失敗するか」「他の検証と同じ故障原因か」「正常な変更や実行環境で不要に失敗しないか」「world や対象 MOD が必要か」を判断する。

| 判断 | 基準 |
| --- | --- |
| 維持 | 独立した故障原因や重要な境界を検出する。 |
| 書き換え | 守る挙動は重要だが、観測が弱い、実装の転記だけ、または不安定である。 |
| 統合 | 同じ入口・故障原因を重複して調べ、名前付きの入力ケースとして表現できる。 |
| 削除 | 定数の転記だけ、または別の検証で同じ故障原因を検出できる。 |
| 移動 | 機能の責務と配置が合わない。 |

同じ helper や最終結果でも、利用入口や故障原因が違うものは重複扱いしない。資源不足と必要量ちょうど、手動取消と期限切れ、付与経路の違いを残す。拒否には正常に受け入れる対照を用意し、常に失敗する処理を正しいと判定しない。

既定の耐久値、レアリティ、演出強度、登録総数、静的 tooltip の全文・順序等の転記は整理対象とする。一方、実消費量、完成品数、演算の違い、設定による分岐、表示データの読取で収納物を変更しないことは残す。登録存在だけの検査を増やさず、起動だけでは保証できない利用先との接続を確認する。

戻り値が入力の受付しか表さない場合は、生成物・消費・詠唱状態等で成立を識別する。必須データの lookup 失敗を `ifPresent` 等で無言に省略しない。期待値を製品実装の計算結果から呼び返して作らず、独立した入力と期待結果を使う。

統合ケースは名前と失敗段階を診断できるようにし、各ケースの状態を独立させる。全ケース完了前に `helper.succeed()` を呼ばない。非同期ケースの直列化は時間短縮とは限らないため、件数削減だけで統合しない。削除・統合では失う検証と残る検出経路を簡潔に説明し、恒久的な全件対応表は作らない。

## 3. 機能別の配置

`jp.aquafactory.apprenticecodex.gametest` 配下を、まず機能領域、その下を必要な個別機能で分ける。以下は配置先の目安であり、空のパッケージを先に作る必要はない。

```text
gametest/
  equipment/       # 装備の使用・消費・状態遷移、装備固有の連携
  enchantment/     # 共通の付与・取得・排他・属性ルール
  spell/          # 魔法、照準、対象選択
  effect/         # 複数機能で共有する効果の計算・更新
  storage/        # 収納、保存、旧形式の復元
  crafting/       # 作業台、醸造、調整、レシピ
  world/          # 村人、村構造物
  loot/           # loot の選択と利用経路
  runtime/        # 起動構成、登録・通信等の接続
  integration/    # 複数機能にまたがる外部 MOD 連携
  support/        # 複数機能で実際に共有する小さな補助処理
```

特定装備の Better Combat 連携は装備側へ、複数機能で共有する Forge packet の観測は `runtime` / `support` 等へ置ける。外部 MOD 名だけを唯一の分類軸にしない。パッケージ分類は実行プロファイルの選択機構ではない。

巨大な `ApprenticeCodexGameTestScenarios` と、それに依存する入口・継承先を機能単位で分割する。`ApprenticeCodexEquipmentAndEnchantGameTests` のように複数責務を持つ入口も対象とする。行数の機械的な上限は設けない。

単純なテストは入口に直接書いてよい。シナリオへ委譲する場合は同じ機能パッケージから探せるようにする。機能内の fixture・観測・後片付けを優先し、巨大な共通親クラスを別名で再作成しない。移動の都合だけで製品コードや全シナリオの公開範囲を広げない。

移動時には `@GameTestHolder`、`@PrefixGameTestTemplate`、template 参照、batch と前後処理、登録 ID、フィルター、jar 除外を確認する。現在の `src/main/java/.../gametest` と `data/apprenticecodex/structures/gametest` の配布除外を維持する。配置変更と削除・期待値変更は区別し、移動だけの段階では登録名・数等を照合して欠落と重複を防ぐ。

## 4. 1.20.1 固有の検証経路

main と同じ期待結果でも、実際に通す接続は 1.20.1 の実装に合わせる。

| 領域 | 維持・追加を判断する境界 |
| --- | --- |
| Capability | 取得成功時の更新と、entity 除去後など取得不能時の既定値・副作用なしを分ける。消費・召喚等を成功確認前に実行しないことを確認する。 |
| NBT・収納 | 現形式の保存前と復元後、旧形式の読取と初回変更、未知データ・収納物・装着物の維持を分ける。読込修復が保存前の不具合を隠さないようにする。 |
| エンチャント・修理 | 付与条件、取得、排他、効果を分ける。テーブル、本、金床合成、強制付与後の効果、修理素材は異なる経路として扱い、Java override / Forge hook と実際のメニューの接続を確認する。 |
| 装備・Curios | modifier 定義だけでなく装備後の属性、交換・再装備時の非重複、解除後の復元を確認する。属性演算の差や学派の取り違えを見分けられる入力にする。 |
| Forge イベント・Mixin | helper 直呼びと実イベント経由を区別する。依存 MOD の対象バージョンで接続し、取消・消費・更新順が成立することを確認する。 |
| データ | 1.20.1 の `recipes`、タグ、loot、structure 等を実際の manager / 利用入口から確認する。1.21.1 の配置・schema へ置き換えない。 |
| 通信 | 本番で選ぶ packet、登録 channel、方向、wrapper、encode/decode、handler と結果を分ける。Codec の往復だけを通信成立と扱わない。 |

FakePlayer、未登録 player、world 登録済み player は用途を分ける。手動 `tick()` が装備更新、イベント、UUID 解決まで代行するとは扱わない。必要に応じて接続付き ServerPlayer や通常の更新経路を使い、対象 MOD の型前提と整合させる。Curios の検索 cache や tick 前後の更新順は、その版の実装を確認する。

禁止設定では判定 helper だけでなく利用入口との接続を確認する。保存後に禁止へ切り替えた場合の拒否・資源維持と、再許可後の成功を分ける。現在の挿入規則を使って旧データを生成し、保存済み資産の読取・取外しを検証不能にしない。

## 5. PR #1035 からの回帰検証方針

PR #1035 では、大鎌投擲時の client 側アニメーション停止で、Better Combat の `AttackAnimation` を Forge の `SimpleChannel` へ直接送っていた経路を修正した。1.20.1 の当該 channel は `PacketWrapper` を登録するため、依存側の `ClientPlayNetworking.send(id, buffer)` を経由して包む必要があった。参照時点のローカル依存の IDE 定義でも、この API が `PacketWrapper(false, id, forwardBuffer)` を送ることを確認した。

この不具合はサーバー側の大鎌投擲・消費・帰還が成功しても残り得る。整理では次の保証を分ける。

| 確認範囲 | 検出したいこと・限界 |
| --- | --- |
| 大鎌の server GameTest | 投擲・帰還・消費・状態解放。client の停止通知送信は通らない。 |
| Forge 通信の接続検証 | 本番の送信経路が選んだ型・ID・方向を、登録済み channel で変換できること。テストだけで正しい wrapper を新しく作って成功させても、本番の誤送信は検出できない。 |
| 依存 API の静的確認 | 固定した依存版の登録型と送信 API の対応、client / optional 型境界。実通信の成功は保証しない。 |
| 人間による client 確認 | Better Combat 導入下の実操作で停止通知・投擲が成立し、クラッシュや残留モーションがないこと。 |

通信の自動回帰テスト候補は、本番経路と共有する送信メッセージの選択・構築と、実登録 channel への変換までを対象とする。旧方式の直接送信へ戻した場合に失敗するかを設計の判断基準にする。既存 `ForgePacketTestSupport` は S2C の観測補助であり、その成功を C2S の証明に流用しない。wire discriminator の固定値の転記も避ける。

ただし現状の `BetterCombatScytheThrowClientCompat.stopSwing()` は Minecraft client とアニメーション型に依存する。このメソッドを dedicated server GameTest からロードして直接呼ぶ設計にはしない。共通化できる処理があるか、依存の登録・変換を server で安全に呼べるかを実装時に確認する。必要なら小さな接続補助の抽出を別変更として判断し、モック送信先を呼んだだけで実 channel 接続まで検証済みとしない。自動化できない部分は静的確認と人間確認へ明示的に残す。

人間向けの具体例は、`runClientBetterCombat` で大鎌を持ち、通常攻撃から投擲操作へ移り、投擲成立、残留する攻撃モーション、クラッシュ、帰還後の再攻撃を確認すること。通常構成での投擲も対照にする。これは今後その連携に触れた変更で引き継ぐシナリオであり、この文書の追加だけで client の起動や再確認を要求しない。通常の Codex 検証として client 自動操作を追加しない。

## 6. 実行構成と安定性

機能・計算の自動テストは原則として GameTest にまとめ、各 `runGameTestServer...` を対応構成の一式を確認する入口とする。純粋計算は world 状態を参照せず明示的な入力・時刻で検証する。JUnit 等の別基盤は高速な反復の必要が明確になった段階で、全件実行入口と運用負担も含めて再検討する。

optional MOD が必要な構成では、既存の `apprenticecodex.requiredOptionalMods` によるロード確認を維持する。不在時に成功として省略したケースを連携成功に数えない。対象 MOD 導入下で実際の分岐に到達することと、不在時に外部型を読まず起動することを別々に確認する。main の Accessories 等の非互換テストや実行プロファイルをそのまま持ち込まない。既知の上流不具合を観測する任意テストと、不安定な必須テストの任意化を区別する。

既存の `GameTestFixtureSupport` の chunk 待機と `GameTestConfigIsolation` の設定監視隔離は、1.20.1 固有の前提として扱う。移動時も起動・登録が維持されることを確認し、main と揃えるためだけに外さない。設定監視隔離下の成功は、通常サーバーや client の設定再読込の保証にはしない。

- 相対座標と絶対座標を入口で区別し、飛行・探索・衝突範囲と entity の AABB を含む template を選ぶ。1.20.1 の構造配置による整地範囲も考慮する。
- entity の参照保持、追加成功、chunk 読込、UUID 検索、空間検索、entity-ticking は別の前提として必要なものを確認する。手動 tick で登録や他 entity の更新を代用しない。
- 自分の生成物を UUID・owner・同期操作中のイベント等で識別する。近隣の同種 entity の総数や、生成しなくても成立する最終空集合だけで判定しない。
- 準備と操作は一度実行し、待機 callback では観測する。非同期処理は完了条件と期限を持たせ、二重消費等の否定条件には必要な観測期間を確保する。
- config は変更前の値へ戻し、生成物、共有状態、listener、接続、buffer を失敗・timeout 時にも解放する。自然な終了の assertion より前に後片付けして不具合を隠さない。
- 乱数の特定結果を有限回の試行で必須にしない。必要な分岐を制御し、共有 world の乱数を書き換えて他のテストへ影響させない。
- 距離・期限・拒否境界を緩めたり、リトライや `required = false` だけで不安定さを隠したりしない。対象、段階、位置、経過 tick、期待値・実測値を英語で診断する。

再実行の成功と原因の解消を区別する。実行対象・source・構成が同じ追加実行と、fixture 等を修正した後の実行を混同しない。GameTest の直列実行、Java 17、強制終了 timeout、失敗報告の規則は AGENTS.md を維持する。

## 7. 着手順と各段階の完了条件

次の順を目安とし、一度の変更で全領域を整理しない。

1. **対象機能の棚卸し**: 現在の入口、シナリオ、共有親への依存、template、構成、検出する故障原因を確認する。main の完成形と比較し、共通・Forge 固有・対象外を短く説明できる状態にする。
2. **配置と依存の整理**: 巨大な共通シナリオから一機能ずつ分離する。入口も同じ領域へ移し、必要な小さな補助処理だけ抽出する。ここでは既存の検証意図・期待値を維持し、登録漏れ・重複と配布除外を確認する。
3. **検証内容の整理**: 定数転記や重複を削減し、結果・状態遷移・保存前後の観測を改善する。消す検証ごとに残る検出経路または不要な理由を示せるところで区切る。
4. **版固有の接続補強**: 第4・5節に照らし、現在通していない重要な接続を選ぶ。通信・Capability・メニュー・イベント等の不足に絞り、製品コードへの補助抽出が必要なら配置変更と区別する。
5. **検証と引渡し**: Java 17 の build、標準 GameTest と影響する optional 構成を実行し、登録と検出範囲を確認する。人間の確認が必要な部分は該当 Skill に従ってシナリオと未確認範囲を報告する。

初期候補は、大きな共通シナリオに集まる装備・エンチャント領域とする。エンチャントは付与・取得・属性・修理の全体を先に棚卸しし、版の違う API へ局所的に置換し続ける作業を避ける。PR #1035 の通信境界も初期に棚卸しするが、その自動回帰テスト実装を全パッケージ移動の前提にはしない。

共有 helper や登録機構の広い変更では、それを使う全構成へ検証範囲を広げる。全構成を確認する際も GameTest は一つずつ直列で実行する。CI の必須条件や実行対象を変える場合は、この整理と別に影響を判断し、既存の文書更新規則に従う。

完了条件は、採用した変更の検証が済み、意図した検出経路が残り、意図しない登録欠落がないこと。件数の一致・削減や全ファイルの命名統一は条件にしない。統合を見送る判断も完了に含め、関連しない機能の網羅テスト追加へ広げない。作業用の件数台帳や対応表は必要な期間だけ使い、長期に残す教訓はこの方針へ集約する。
