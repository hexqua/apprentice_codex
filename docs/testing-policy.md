# テスト設計・整理方針

この文書は Apprentice's Codex のテストを追加・修正・整理するときの初版方針を定める。[Constellation 'n Spells のテスト設計方針](https://github.com/hexqua/constellation_n_spells/blob/79fc7b78147feb13c7ef586a45f078f8e1049e42/docs/testing-policy.md)を参考に、本 MOD の装備、魔法、収納、optional MOD 連携と既存 GameTest の整理に合わせている。

この方針を最終形として固定しない。今後のテスト修正で分類、分割単位、実行方法などに不都合が分かった場合は、理由を説明して関連する方針も同じ変更で見直す。既存テストすべての即時適合は要求せず、機能単位で段階的に整理する。

実行コマンド、必要な検証、失敗時の報告、client 検証の分担は [AGENTS.md](../AGENTS.md) に従う。この文書の制定だけでは、既存テストや CI の実行対象を変更しない。

## 1. 検証するもの

実プレイで起きる不具合を検出できる処理結果、状態遷移、Minecraft・依存 MOD・データとの接続を優先する。

- 詠唱の成立・拒否、弾の命中、ダメージ、マナ・弾薬・耐久値の消費を確認する。
- 装備・交換・解除、収納・取り出し、開始・中断・終了後の結果を確認する。
- 保存・読込、旧データの復元、アイテムの返却など、既存資産の保護を確認する。
- レシピ選択、タグ判定、登録された定義の利用先への接続を確認する。
- 所有権、権限、射程、設置・破壊許可、消費の重複防止など、server が守る制約を確認する。

すべてを通常のプレイヤー操作から再現する必要はない。検出したい不具合に必要な経路を通し、直接呼び出し、イベント経由、実通信、client 操作のどこまでを確認したかを明確にする。Codec の往復だけで実通信を、演出状態の計算だけで描画を確認済みとしない。

入力を消費したことや要求を受け付けたことを示す戻り値だけで、発動成功を判定しない。失敗時にも同じ戻り値を返す経路では、recast残数の減少、詠唱状態、生成物、消費、ダメージ等、その操作の成立を識別できる結果を確認する。

禁止設定や許可リストは、判定helperだけでなく実際の利用入口との接続を確認する。保存・収納後に設定を変更した場合の拒否、拒否時の資源・状態の維持、設定を戻した後の利用成功を区別する。別機能の独立した設定まで影響しないことも、必要な境界として扱う。

## 2. 維持・書き換え・統合・削除・移動の判断

テスト件数の維持・増加や、一定件数までの削減を目的にしない。各テストについて次を確認する。

1. どんな不具合が起きると失敗するか。
2. 起動時チェックや既存テストでも同じ不具合を検出できるか。
3. 正常な仕様変更、乱数、配置、実行順序によって不要な失敗が起きないか。
4. GameTest の world や対象 MOD が本当に必要か。

| 判断 | 基準 |
| --- | --- |
| 維持 | 独立した不具合や重要な境界条件を検出する。 |
| 書き換え | 守りたい挙動は重要だが、観測方法が弱い、実装に追従するだけ、または不安定である。 |
| 統合 | 同じ処理経路と故障原因を重複して検証しており、差分をケースとして表現できる。 |
| 削除 | 定数の転記や、他の検証と保証範囲が重なるだけである。 |
| 移動 | 機能の所属と配置が合わず、検証の責務に沿ったクラス・パッケージへ移す。 |

テスト名だけで削除を決めない。定数確認と挙動確認が混在する場合は、不要な assertion を除き、必要な処理結果を残す。統合時も、無関係な検証を巨大な一件へ集約しない。失敗したケースが診断文字列から分かり、各ケースが独立した状態で実行できるようにする。

保存復元のテストへ統合する場合は、保存前のnormalization直後と、復元・repair後の両方で必要な結果を確認する。読込時の修復が保存前の不具合を隠す可能性があるため、復元後の成功だけを理由に保存前のassertionを削除しない。

削除・統合する変更では、失う検証と残る検出経路、または検証不要と判断した理由を PR 等で簡潔に説明する。恒久的な全件対応表の作成は要求しない。

### 定数・getter・登録

耐久値、レアリティ、光量、演出の強度、既定のバランス値など、設定値を getter で読み返して完全一致を要求するだけの検証は原則追加せず、既存分も整理対象とする。

完成品の個数、実際の消費量、ダメージ、装備後の補正量など、守りたい処理結果の数値は検証してよい。特定の定数自体を固定する必要がある場合は、その値が変わると起きる不具合と固定する理由を示す。

コンテンツ総数や単純な登録存在の網羅確認を増やさない。起動成功だけでは保証できないレシピ選択、タグ解決、POI とブロックの対応など、利用先との接続は残す。

必須の登録データを使う検証では、lookup失敗を `ifPresent` 等で無言に省略しない。必要なデータの存在を前提として明示し、そのデータを使った処理結果まで確認する。optional MOD不在時の意図した省略とは区別する。

共通実装の静的なtooltipキーや順序を全アイテムで固定する検証も、代表ケースや必要な境界へ絞る。設定・依存MODの有無による表示分岐、エラーの内容と引数、保存された状態の反映、表示データを読む際に収納物や選択を変更しないことは、独立した挙動として残す。

### 装備・属性

modifier の属性・演算・量の定義確認だけで終えず、実際の装備処理後の entity の属性値を優先する。正しい部位、交換・再装備での非重複、解除時の復元、必要な組み合わせを確認する。

共通実装は代表装備と境界条件へまとめられるが、独自 override や異なる装備経路を持つものまで無条件に代表一個へ置き換えない。期待値を製品実装の計算結果から再計算するだけにせず、演算の違いも検出できる条件を選ぶ。FakePlayer 等の更新上の制約を踏まえ、必要な装備更新経路を通す。

増加した属性や成功した対象を探して、それを期待する学派・対象として逆算しない。注入・復元された入力データを先に検査し、その入力に対して増えるべき属性と、変わらない属性を区別する。属性の演算を確認するfixtureでは、加算・基礎値への乗算・最終乗算を区別でき、上限への張り付きで差が消えない基礎値を使う。

軽量な mock player がすべての構成で使えるとは限らない。Epic Fight の専用サーバー構成では、PLAYER を ServerPlayer として扱う処理と軽量 mock の型が合わず、client 専用型の読込に至る場合がある。プレイヤーの更新が必要な検証では、必要に応じて mock 接続を備えた ServerPlayer と、Player / LivingEntity の装備更新を通る `doTick()` を使う。接続等のテスト用資源は後片付けし、単なる `tick()` 呼び出しや対象構成での省略で検証を済ませない。

worldへ登録していないplayerを手動更新する場合、worldが発行するイベントまで自動的に通るとは扱わない。Curiosは更新後、Accessoriesは更新前のイベントで装備差分を反映する等、構成によって接続先が異なることがある。通常のtick前後の経路を順序どおりに通し、片側だけの模擬更新による失敗を製品の非互換と断定しない。登録の必要性と更新順をfixtureに明示し、接続の作成途中で失敗した場合も資源を解放する。

### 調整・保存・メニューの境界

同じ対象・期待値を複数の配列の添字で対応させず、対象と期待する挙動を名前付きのケースにまとめる。調整ルール、保存形式、個別装備の効果、メニュー操作は失敗原因が異なるため、独立した準備と検証に分ける。候補一覧と受入れ判定の一致だけでなく、実際の挿入・保存結果、拒否後の状態維持、取り出しまで必要な経路を通す。

旧形式の読取・最初の変更による移行・未変更スロットや未知の付随データの維持を分けて確認する。現在は新規挿入できない内容も、保存済み資産として読取・取外しを保証する。旧データのfixture作成を新規挿入用の受入れAPIへ一律に置き換えない。無効化された収納枠も、表示や取外し可否だけで終えず、実際の取外しと再挿入拒否、再有効化後の利用を区別する。

詠唱元の保持やイベント順を確認するときは、検証対象の計算メソッドを期待値へ呼び返さない。選択元の基準値と独立した入力から期待値を作り、即時処理・遅延処理・取消後を別のplayer状態で確認する。イベントだけの制御入力による検証と、実際の装備更新・詠唱からの検証を区別する。

### バージョン差の大きい機能

エンチャントのようにバージョン間で仕組みが大きく異なる領域は、関連機能全体を一つの整理範囲として扱う。付与条件、取得経路、排他関係、付与後の効果、保存済み資産の維持を分け、共通に守る挙動と、各バージョン固有の定義・登録・イベント・装備更新経路を区別する。テストの配置や API、エンチャント一覧の一致をバージョン間の互換性の証拠にしない。意図された代替機能や、そのバージョンに存在しない機能も個別に扱う。

テーブルでの付与、本の受入れ、金床での合成、コマンド等による強制付与後の効果は、別の経路として判断する。同じ期待値の表を共有しても経路間の差を消さず、判定メソッドの成功だけで実際の付与成功を確認済みとしない。共通の検証意図を先に整理し、テスト用の生成・読取・適用処理は各バージョンで自然な実装にするための小さな補助処理にとどめる。

## 3. クラスとパッケージの整理

従来の `ApprenticeCodexGameTestScenarios` のように多数の無関係な機能を抱える一万行規模のクラスは、積極的な分割対象とする。入口クラスとシナリオクラスの両方を整理し、クラス名だけで機能を区別する平坦な配置から、機能単位のパッケージへ移す。

行数だけの機械的な分割や、厳密な行数上限は設けない。一つの機能の目的・準備・観測・後片付けを追いやすくし、異なる機能の変更が同じ巨大クラスに集中しないことを目指す。

### 配置の考え方

GameTest は原則として `jp.aquafactory.apprenticecodex.gametest` 配下に置き、まず機能領域、その下に必要な個別機能を配置する。次は初期の分類例であり、全パッケージの作成やこの名称への一律統一を要求しない。

```text
gametest/
  enchantment/
    application/
    acquisition/
    attribute/
    support/
  effect/
    castingmobility/
  spell/
    searchbeacon/
    targeting/
  equipment/
    spellgun/
    psychicdrivegauntlets/
    broom/
  storage/
  crafting/
  integration/
    malum/
    epicfight/
  support/
```

- 基本は検証対象の機能を所有するパッケージへ置く。型の種類や `GameTests` / `Scenarios` という役割だけで全機能を分断しない。
- 特定機能の optional MOD 連携は、その機能の近くに置いてよい。複数機能にまたがる連携や外部 API 専用の補助処理は `integration.<mod>` 等へまとめる。外部 MOD 名だけを唯一の分類軸にしない。
- 一つの package に無関係なテストが集まる、または fixture や変更理由が分かれる場合は、さらに機能単位で分ける。一テストごとの過剰な細分化も避ける。
- `core`、`common`、`support` 等へ分類しきれないものを集積し、新しい巨大クラスを作らない。

現在は `equipment`、`spell`、`effect`、`enchantment`、`storage`、`crafting` を主な機能領域とし、村人・村構造物等は `world`、loot は `loot`、起動構成や登録の接続確認は `runtime` に置く。入口とシナリオは同じ機能パッケージから探し、共通ヘルパーへの継承ではなく必要な補助処理を明示して利用する。複数装備に共通する付与・取得・属性ルールは `enchantment`、特定装備の使用・消費・保存や実lootへの接続は、その機能を所有するパッケージへ置く。

複数の魔法・装備で共有する効果そのものの計算・更新は `effect`、その効果を付与する詠唱や装備の成立条件は各機能側へ置く。

パッケージ分類は実行プロファイルの選択機構ではない。フォルダーを移動しただけで通常構成から連携テストが除外されるとは扱わず、対象 MOD を含む構成での検証と不在時の型読込境界を別途確認する。

### クラスの責務とヘルパー

- 同じ機能でも、保存復元、戦闘、装備状態など準備や失敗原因が大きく異なる場合は、クラスを分ける。
- 単純なテストは入口クラスに直接実装してよい。既存の「入口からシナリオへ委譲する」二段構成を全テストに強制しない。
- シナリオを分ける場合は、対応する入口と同じ機能パッケージを基本とし、読み進める先が分かる名前にする。
- fixture、定数、観測、後片付けは、その機能内のヘルパーに閉じる。複数機能で実際に使うものだけを `support` 等へ共通化する。
- パッケージ移動の都合だけで製品コードの可視性を広げたり、全シナリオを public な共通 API にしたりしない。共有が必要な責務を見直してから公開範囲を決める。
- 集計や観測ヘルパー自身の誤りが偽陽性・不安定さを生む場合は、その前提を保証する小さなテストを残してよい。

### 移動時に守ること

パッケージやクラスの移動では、GameTest の探索・登録、アノテーション、template の参照、batch と前後処理、Gradle の対象指定や jar 除外設定を確認する。入口の重複登録や登録漏れを起こさない。テスト名・ID が変わる場合は、実行フィルターや関連する参照への影響を確認する。

配置整理とテストの削除・期待値変更は、可能な範囲で差分やコミットを分ける。移動だけの段階では、対象テストの登録数・名前等を照合し、意図しない検証の欠落を防ぐ。既存の batch 分離や optional MOD の不在時の型読込境界を崩さない。

## 4. 実行環境と optional MOD

機能・計算の自動テストは原則として GameTest にまとめ、各 `runGameTestServer...` を対応構成のテスト一式を確認する入口とする。普段から全件を実行する運用では、実行入口と確認範囲をそろえ、実行漏れや基盤の管理負担を抑えることを優先する。

純粋計算もワールド状態を参照しない独立した GameTest として配置し、明示的な入力や時刻で確認する。registry・装備更新・イベント・保存復元との接続は、それぞれの経路を通す検証として区別する。JUnit等の別基盤は、計算部分だけを高速に繰り返し確認する必要が明確になった時点で再検討する。その際も、既存の全件実行の入口から検証が漏れない方法と、導入による運用負担を合わせて判断する。

必須 MOD のロード確認だけの重複検証は増やさない。optional MOD の検証構成では、要求 MOD が実際に読み込まれていることを確認し、連携処理を通らず成功することを防ぐ。

対象 MOD 不在で成功として省略するテストは、連携を検証済みと数えない。整理時は対象プロファイルでの選択・登録を検討するが、通常構成で外部型を読み込まず起動できることは別の保証として残す。プロファイル選択の仕組みを変える場合は、標準・対象構成それぞれの実行対象を確認する。

Accessories 等の既知の非互換の観測と、上流修正検知用の任意テストは、通常の互換性保証と分けて扱う。flaky な必須テストの一括任意化とは区別する。

## 5. 安定性と後片付け

重要な挙動を検証する flaky テストは、件数削減とは別に実行条件と観測方法を改善する。リトライ回数や timeout の増加、`required = false` 化だけで解決したことにしない。

- entity と探索・移動範囲は template と必要な chunk の tick 範囲を踏まえて設計する。範囲外の検証が必要なら、その読込・tick 条件を明示的に保証する。
- 自分が生成した entity やイベントを特定し、近隣テストの振動、ドロップ、攻撃等を誤って観測しない。イベントの否定検証は発生源を絞り、同じ観測方法の肯定検証も用意する。観測期間を短縮して干渉を避けない。
- config、共有 player 状態、登録したリスナー等は適切に復元・解除する。遅延処理中に失敗した場合も後片付けが走るようにし、生成したentity、mock接続、packet用bufferも解放する。共有設定は既定値へresetするだけでなく、変更前の値へ戻す。batch 分離だけに依存しない。
- AI、日光、天候、物理移動等は、検証目的に必要なものと環境ノイズを区別する。tick していないだけで成功する偽陽性にも注意する。
- 有限回の乱数試行で最大値等の特定結果が必ず出ることを要求しない。不変条件を確認するか、必要な状態を明示的に作る。固定 seed だけでこの問題を解決したとしない。
- 遅延・非同期処理には完了条件と期限を設ける。二重ヒットや再消費がないこと等の否定条件には、必要な観測期間を確保する。
- 失敗時は、対象、位置、段階、経過 tick、期待値と実測値など、原因を絞れる診断を英語で出す。

失敗頻度を調べる場合は、同じsource・プロファイル・実行対象で完走した回数と、対象テストの失敗回数を対応させる。対象MOD不在による省略を成功回数に含めず、作業途中の変更をまたいだ実行履歴、診断追加後、fixture修正後の測定は区別する。少数回の成功だけで低頻度の失敗がないとは判断せず、過去の単発失敗から外部MODの動作が不安定とも断定しない。

登録候補から抽選する処理では、必要に応じて候補集合の検証と、制御した選択による実処理の検証を組み合わせる。各候補を一度ずつ選ぶ等の方法で、取得できるべきものと除外すべきものを確認する。固定seedを多数試して全種が出現することを要求せず、依存MOD等で候補集合が変わっても、選択対象の取り違えを識別できる条件にする。

メニュー経由の検証では、入力アイテムが処理可能であること、候補・完成品が実際に生成されていることを先に確認する。テーブル等の周辺ブロック条件、近傍player検索に必要なworldへの登録、同じ入力を再評価する際のseedや状態も準備に含める。ブロック、player、メニュー等を変更した場合は失敗時にも復元する。候補データの更新確認だけで画面の描画まで確認済みとしない。

### 相対座標と生成元の観測

GameTest helperへ渡す相対座標と、Level・直接の詠唱helper等へ渡す絶対座標を区別する。同じ相対座標を直接APIへ渡すと、複数テストがworld原点付近を共有し、別テストの生成物を数えたり、自分の発動先とは異なる場所で「残存なし」を確認したりする。直接呼出しの入口で絶対座標へ変換し、射線・投影先・生成物を収めるtemplateを用意する。

生成物をイベントで捕捉する場合は、自分の同期操作中に生成した個体と、そのownerから後で生成される個体を識別する。周辺の同種entityの総数を代替にしない。終了時の強制的な解放が欠陥を隠さないよう、自然な終了・取消による状態の解放を先にassertし、残ったテスト用資源を成功・失敗・timeoutの全経路で後片付けする。観測helperを広く使う場合は、近隣の無関係な個体を除外し、途中失敗でも自分の資源だけを解放できることを確認する。

ownerを取得するAPIがない生成物は、自分の同期操作中に発生した生成イベントで捕捉する。手動tick中に派生物を生成する検証では、そのtick自体も捕捉区間に含める。後のworld tickで生成する個体には別途識別条件を用意し、周辺検索への置換で済ませない。射手と壁・標的・生成物の座標変換は同じfixtureにそろえ、専用templateの拡張後も相対位置を維持する。

採掘dropを追跡するときは、同期操作中の生成物に加え、破壊者と破壊座標が一致する採掘イベントの実体・UUIDを利用できる。外部MODがイベントを取り消して運搬用に保管した場合、捕捉したItemEntityが存在するだけでは排出済みとみなさず、Levelへの実登録または対象playerへの受け渡しを確認する。直接採掘分を除外する場合も、自分の操作で生成した分だけを除外し、周辺itemを一括削除しない。

### 範囲外のentityと手動tick

小さいtemplateを使いながら標的や探索・飛行経路を外へ伸ばすと、配置座標や周辺chunkの読込状態によって成否が変わる。高さだけを変えて他のテストから離しても、水平範囲の管理は保証されない。必要な距離を収める専用templateを使い、標的、移動後の位置、投射物の後方・横方向への広がりも含めて範囲を決める。

生成位置には目線からの上下・前方オフセットも含める。設置ブロックが範囲内でも、召喚物が床より下へ出ることがある。範囲チェックを緩めず、設置高と床上の空間を準備する。

移動先の中心が空気でも、移動途中のAABBが床や側面に触れると移動量は変わる。特に下降を伴う水中移動では、隣接する床まで含めた移動範囲の衝突を準備段階で検査し、速度制限による減速とfixtureへの衝突を区別する。

Lock On Rayの到達時刻検証では、5×5のtemplateから64block先へ置いた標的について、生成直後からchunk未読込・UUID検索不可となる配置を確認した。レーザーは標的を失った場合に直進するため、手動でtickを進めても予定時刻に着弾しない。距離や期限を緩めず、射線を収めるtemplateと生成時の前提検査で修正する。

`addFreshEntity` の成功、Javaのentity参照の保持、chunkの読込、UUID検索での取得、entity-tickingは別の状態である。検証する経路に合わせ、必要な前提を生成時と移動時に確認する。手動の `tick()` 呼び出しは、world側のentity登録・chunkの可視性・他entityの更新を代行しない。追加のchunk読込が本当に仕様上必要な検証ではその範囲と復元を明示し、配置ミスを隠すための強制読込は行わない。

未読込の移動先を検証する場合は、飛行前にそのchunkが未読込であることを確認する。template拡張や全件実行の配置によって周辺chunkの読込範囲は変わるため、固定距離だけで未読込と仮定しない。

再発時には、ケースの距離と移動条件、予定到達tickと実tick、弾・標的の位置、生存・削除状態、UUID検索の結果、chunkの読込・tick状態、実際の命中先を記録する。これにより、標的喪失、別entityへの命中、ダメージ拒否、計算・到達時刻の問題を分けて調べられる。

### その他の不安定化しやすい準備・観測

| 条件 | 起きる問題 | 設計・診断の要点 |
| --- | --- | --- |
| FakePlayerや軽量mockの更新を通常playerと同一視する | 空のtickで装備更新を通せない、依存MODが要求するserver側の型と合わない | 属性を検証する場合は必要に応じて接続付きServerPlayerの `doTick()` を使い、装備後・解除後の実値を確認する |
| 装備検索後、同tickに装備を変えて即座に再検索する | Curios等のtick単位の検索cacheが変更前の結果を返す | 装備済みfixtureを最初から作る。装備変更そのものの検証では、実際の更新順とcacheの有効期間を通して確認する |
| 薬莢返却等の特定の抽選結果を有限回の試行で要求する | 正しい実装でも期待した出目が一度も出ず失敗する | 分岐が重要なら出目を直接制御する。匿名player等で乱数を差し替える際は、ローカル変数名が継承フィールドに隠されて元の乱数を返していないかも確認する |
| 最終成功callbackにだけ後片付けを置く | 途中のassertion失敗やtimeoutで予約・再装填状態、listener、config等が残り後続へ影響する | 同期処理は `try/finally`、複数tickの処理は終了・失敗通知で復元する。listenerは自分が生成したentityを絞って観測する |
| 非同期読込や別entityの更新完了を、根拠のない固定tickだけで確認する | 必要な読込や更新が完了する前に観測して失敗する | 状態遷移の完了条件と期限を使う。到達時刻などtick数そのものが仕様である場合は期待値を維持し、必要な入力・登録・更新条件を先に保証する |
| drop等を地面とinventoryだけで観測する | 運搬entityや内部bufferへの一時保管と消失を区別できない | 生成時に自分のentityを捕捉し、削除・検索範囲外への移動後も位置、tick進行、目的地、内部保管を診断する。受取完了を守るテストでは、内部保管だけを成功条件へ足さない |

再実行で成功しても原因が解消したとは判断しない。同じsourceでの追加実行と、fixture・製品コード・期待値を変えた後の実行を区別する。診断で範囲不足を確認した場合も、単なる配置調整だけで終えず、必要な距離・移動・拒否境界を維持したまま検証できることを確認する。

## 6. 段階的な整理

最初は装備・エンチャント等の大きな領域と巨大な共通シナリオから、対象機能を選んで進める。各変更で対象範囲を定め、配置整理、不要な検証の削減、観測方法の改善、実行先の変更を区別する。一度の変更で全機能の移動や共通ヘルパーの全面再設計を要求しない。

機能別の棚卸し文書は、整理を進めるために必要な期間に限定する。一段落したら共通の判断基準・教訓をこのポリシーへ移し、役目を終えた個別文書は削除する。個別の件数台帳や全件対応表を常設せず、実施内容はコードとコミット、作業報告から追跡する。

整理後は AGENTS.md に従って build と影響範囲の GameTest を実行する。件数の減少だけで完了とせず、重要な故障原因が引き続き検出され、意図しない登録漏れがないことを確認する。人間による client 確認が必要な範囲は既存の分担に従って引き継ぐ。

共通の検証意図は backport 先でも利用できるようにするが、loader 固有の探索・登録・データ API まで同じ構成を強制しない。実際の backport は対応する Skill とブランチの検証手順に従う。
