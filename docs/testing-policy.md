# テスト設計・整理方針

この文書は Apprentice's Codex のテストを追加・修正・整理するときの初版方針を定める。[Constellation 'n Spells のテスト設計方針](https://github.com/hexqua/constellation_n_spells/blob/79fc7b78147feb13c7ef586a45f078f8e1049e42/docs/testing-policy.md)を参考に、本 MOD の装備、魔法、収納、optional MOD 連携と既存 GameTest の整理に合わせている。

この方針を最終形として固定しない。今後のテスト修正で分類、分割単位、実行方法などに不都合が分かった場合は、理由を説明して関連する方針も同じ変更で見直す。既存テストすべての即時適合は要求せず、機能単位で段階的に整理する。

実行コマンド、必要な検証、失敗時の報告、client 検証の分担は [AGENTS.md](../AGENTS.md) に従う。この文書の制定だけでは、既存テストや CI の実行対象を変更しない。

## 1. 検証するもの

実プレイで起きる不具合を検出できる処理結果、状態遷移、Minecraft・依存 MOD・データとの接続を優先する。

- 詠唱の成立・拒否、弾の命中、ダメージ、マナ・弾薬・耐久値の消費を確認する。
- 装備・交換・解除、収納・取り出し、開始・中断・終了後の結果を確認する。
- 保存・読込、旧データの復元、アイテムの返却など、既存資産の保護を確認する。
- レシピ選択、タグ判定、登録された定義の利用先への接続を確認する。
- 所有権、権限、射程、設置・破壊許可、消費の重複防止など、server が守る制約を確認する。

すべてを通常のプレイヤー操作から再現する必要はない。検出したい不具合に必要な経路を通し、直接呼び出し、イベント経由、実通信、client 操作のどこまでを確認したかを明確にする。Codec の往復だけで実通信を、演出状態の計算だけで描画を確認済みとしない。

## 2. 維持・書き換え・統合・削除・移動の判断

テスト件数の維持・増加や、一定件数までの削減を目的にしない。各テストについて次を確認する。

1. どんな不具合が起きると失敗するか。
2. 起動時チェックや既存テストでも同じ不具合を検出できるか。
3. 正常な仕様変更、乱数、配置、実行順序によって不要な失敗が起きないか。
4. GameTest の world や対象 MOD が本当に必要か。

| 判断 | 基準 |
| --- | --- |
| 維持 | 独立した不具合や重要な境界条件を検出する。 |
| 書き換え | 守りたい挙動は重要だが、観測方法が弱い、実装に追従するだけ、または不安定である。 |
| 統合 | 同じ処理経路と故障原因を重複して検証しており、差分をケースとして表現できる。 |
| 削除 | 定数の転記や、他の検証と保証範囲が重なるだけである。 |
| 移動 | 機能の所属と配置が合わない、またはより軽量な実行環境で十分に検証できる。 |

テスト名だけで削除を決めない。定数確認と挙動確認が混在する場合は、不要な assertion を除き、必要な処理結果を残す。統合時も、無関係な検証を巨大な一件へ集約しない。失敗したケースが診断文字列から分かり、各ケースが独立した状態で実行できるようにする。

削除・統合する変更では、失う検証と残る検出経路、または検証不要と判断した理由を PR 等で簡潔に説明する。恒久的な全件対応表の作成は要求しない。

### 定数・getter・登録

耐久値、レアリティ、光量、演出の強度、既定のバランス値など、設定値を getter で読み返して完全一致を要求するだけの検証は原則追加せず、既存分も整理対象とする。

完成品の個数、実際の消費量、ダメージ、装備後の補正量など、守りたい処理結果の数値は検証してよい。特定の定数自体を固定する必要がある場合は、その値が変わると起きる不具合と固定する理由を示す。

コンテンツ総数や単純な登録存在の網羅確認を増やさない。起動成功だけでは保証できないレシピ選択、タグ解決、POI とブロックの対応など、利用先との接続は残す。

### 装備・属性

modifier の属性・演算・量の定義確認だけで終えず、実際の装備処理後の entity の属性値を優先する。正しい部位、交換・再装備での非重複、解除時の復元、必要な組み合わせを確認する。

共通実装は代表装備と境界条件へまとめられるが、独自 override や異なる装備経路を持つものまで無条件に代表一個へ置き換えない。期待値を製品実装の計算結果から再計算するだけにせず、演算の違いも検出できる条件を選ぶ。FakePlayer 等の更新上の制約を踏まえ、必要な装備更新経路を通す。

## 3. クラスとパッケージの整理

`ApprenticeCodexGameTestScenarios` のように多数の無関係な機能を抱える一万行規模のクラスは、積極的な分割対象とする。入口クラスとシナリオクラスの両方を整理し、クラス名だけで機能を区別する平坦な配置から、機能単位のパッケージへ移す。

行数だけの機械的な分割や、厳密な行数上限は設けない。一つの機能の目的・準備・観測・後片付けを追いやすくし、異なる機能の変更が同じ巨大クラスに集中しないことを目指す。

### 配置の考え方

GameTest は原則として `jp.aquafactory.apprenticecodex.gametest` 配下に置き、まず機能領域、その下に必要な個別機能を配置する。次は初期の分類例であり、全パッケージの作成やこの名称への一律統一を要求しない。

```text
gametest/
  spell/
    searchbeacon/
    targeting/
  equipment/
    spellgun/
    psychicdrivegauntlets/
    broom/
    enchantment/
  storage/
  crafting/
  integration/
    malum/
    epicfight/
  support/
```

- 基本は検証対象の機能を所有するパッケージへ置く。型の種類や `GameTests` / `Scenarios` という役割だけで全機能を分断しない。
- 特定機能の optional MOD 連携は、その機能の近くに置いてよい。複数機能にまたがる連携や外部 API 専用の補助処理は `integration.<mod>` 等へまとめる。外部 MOD 名だけを唯一の分類軸にしない。
- 一つの package に無関係なテストが集まる、または fixture や変更理由が分かれる場合は、さらに機能単位で分ける。一テストごとの過剰な細分化も避ける。
- `core`、`common`、`support` 等へ分類しきれないものを集積し、新しい巨大クラスを作らない。

### クラスの責務とヘルパー

- 同じ機能でも、保存復元、戦闘、装備状態など準備や失敗原因が大きく異なる場合は、クラスを分ける。
- 単純なテストは入口クラスに直接実装してよい。既存の「入口からシナリオへ委譲する」二段構成を全テストに強制しない。
- シナリオを分ける場合は、対応する入口と同じ機能パッケージを基本とし、読み進める先が分かる名前にする。
- fixture、定数、観測、後片付けは、その機能内のヘルパーに閉じる。複数機能で実際に使うものだけを `support` 等へ共通化する。
- パッケージ移動の都合だけで製品コードの可視性を広げたり、全シナリオを public な共通 API にしたりしない。共有が必要な責務を見直してから公開範囲を決める。
- 集計や観測ヘルパー自身の誤りが偽陽性・不安定さを生む場合は、その前提を保証する小さなテストを残してよい。

### 移動時に守ること

パッケージやクラスの移動では、GameTest の探索・登録、アノテーション、template の参照、batch と前後処理、Gradle の対象指定や jar 除外設定を確認する。入口の重複登録や登録漏れを起こさない。テスト名・ID が変わる場合は、実行フィルターや関連する参照への影響を確認する。

配置整理とテストの削除・期待値変更は、可能な範囲で差分やコミットを分ける。移動だけの段階では、対象テストの登録数・名前等を照合し、意図しない検証の欠落を防ぐ。既存の batch 分離や optional MOD の不在時の型読込境界を崩さない。

## 4. 実行環境と optional MOD

world、registry、entity、イベント、依存 MOD との接続が必要な検証は GameTest に残す。独立した計算や状態変換は、Minecraft 起動なしで成立するかを確認したうえで軽量なテストへの移動を検討する。軽量化のために接続部分の保証を失わず、全件の移行を先に要求しない。

必須 MOD のロード確認だけの重複検証は増やさない。optional MOD の検証構成では、要求 MOD が実際に読み込まれていることを確認し、連携処理を通らず成功することを防ぐ。

対象 MOD 不在で成功として省略するテストは、連携を検証済みと数えない。整理時は対象プロファイルでの選択・登録を検討するが、通常構成で外部型を読み込まず起動できることは別の保証として残す。プロファイル選択の仕組みを変える場合は、標準・対象構成それぞれの実行対象を確認する。

Accessories 等の既知の非互換の観測と、上流修正検知用の任意テストは、通常の互換性保証と分けて扱う。flaky な必須テストの一括任意化とは区別する。

## 5. 安定性と後片付け

重要な挙動を検証する flaky テストは、件数削減とは別に実行条件と観測方法を改善する。リトライ回数や timeout の増加、`required = false` 化だけで解決したことにしない。

- entity と探索・移動範囲は template と必要な chunk の tick 範囲を踏まえて設計する。範囲外の検証が必要なら、その読込・tick 条件を明示的に保証する。
- 自分が生成した entity やイベントを特定し、近隣テストの振動、ドロップ、攻撃等を誤って観測しない。
- config、共有 player 状態、登録したリスナー等は適切に復元・解除する。遅延処理中に失敗した場合も後片付けが走るようにする。batch 分離だけに依存しない。
- AI、日光、天候、物理移動等は、検証目的に必要なものと環境ノイズを区別する。tick していないだけで成功する偽陽性にも注意する。
- 有限回の乱数試行で最大値等の特定結果が必ず出ることを要求しない。不変条件を確認するか、必要な状態を明示的に作る。固定 seed だけでこの問題を解決したとしない。
- 遅延・非同期処理には完了条件と期限を設ける。二重ヒットや再消費がないこと等の否定条件には、必要な観測期間を確保する。
- 失敗時は、対象、位置、段階、経過 tick、期待値と実測値など、原因を絞れる診断を英語で出す。

## 6. 段階的な整理

最初は装備・エンチャント等の大きな領域と巨大な共通シナリオから、対象機能を選んで進める。各変更で対象範囲を定め、配置整理、不要な検証の削減、観測方法の改善、実行先の変更を区別する。一度の変更で全機能の移動や共通ヘルパーの全面再設計を要求しない。

整理後は AGENTS.md に従って build と影響範囲の GameTest を実行する。件数の減少だけで完了とせず、重要な故障原因が引き続き検出され、意図しない登録漏れがないことを確認する。人間による client 確認が必要な範囲は既存の分担に従って引き継ぐ。

共通の検証意図は backport 先でも利用できるようにするが、loader 固有の探索・登録・データ API まで同じ構成を強制しない。実際の backport は対応する Skill とブランチの検証手順に従う。
